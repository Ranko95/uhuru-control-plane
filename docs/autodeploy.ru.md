# Автодеплой Control Plane

Push в `main` запускает [workflow](../.github/workflows/deploy.yml) на GitHub Actions:
Node 24.21, `npm ci --ignore-scripts`, typecheck, все HTTP/БД-тесты с отдельным
PostgreSQL 16 и проверки deployment scripts. Затем по SSH на `87.251.77.65:48222`
передаётся проверенный SHA. Можно повторить запуск через Actions → Check and deploy
→ Run workflow, выбрав `main`; проверки выполняются снова.

Одновременно выполняется один workflow, начатые запуски не отменяются новым push.
Ожидающие промежуточные запуски могут быть заменены новым. VPS также проверяет,
что SHA соответствует текущему `origin/main`, до подготовки и перед переключением:
устаревший SHA пропускается, непроверенный новый SHA вместо него не разворачивается.
Если последний push не прошёл проверки, текущая версия продолжает работать.

## Разовая настройка существующего VPS

Подготовьте отдельный Ed25519 SSH-ключ. Приватная часть передаётся только в
GitHub Actions Secret `CONTROL_PLANE_DEPLOY_KEY`. Публичную часть вместе с файлами
`deploy/setup-autodeploy.sh` и `deploy/uhuru-deploy` загрузите во временный каталог
VPS, сохраняя scripts в одном каталоге. На VPS выполните:

```sh
sudo bash /path/to/setup-autodeploy.sh /path/to/deploy_key.pub
```

Установщик переносит существующий чистый checkout в `/opt/uhuru-repo`, сохраняет
текущий код с установленными зависимостями в `/opt/uhuru-releases/<SHA>` и создаёт
ссылку `/opt/uhuru`. Работающий процесс продолжает использовать прежнюю версию;
установщик его не перезапускает. GitHub read-only deploy key из существующего
`core.sshCommand` продолжает использоваться для скачивания репозитория.

Устанавливаются root-owned `/usr/local/sbin/uhuru-deploy`, пользователь
`uhuru-deploy` с forced command и точечным sudo, пользователь `uhuru-build` для
установки npm-зависимостей, а также systemd drop-in с `TimeoutStopSec=10s`.
Если SSH уже использует `AllowUsers`, установщик добавляет отдельный drop-in
с `uhuru-deploy` и выполняет reload после `sshd -t`. Существующий список сохраняется:
повторные директивы [AllowUsers дополняют его](https://man.openbsd.org/sshd_config#AllowUsers).
У `uhuru-deploy` нет права изменять `authorized_keys`, deployment script или
системные настройки. SSH forwarding, PTY и произвольные команды отключены.
Единственная допустимая команда ключа — `deploy <40 lowercase hex characters>`.

Второй GitHub Actions Secret — `CONTROL_PLANE_KNOWN_HOSTS`. Его значение —
строка host key, полученная через уже доверенное SSH-соединение к VPS:

```text
[87.251.77.65]:48222 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIPzXFBLa1QtHKFLXHOoT2RL4eahm++b4kaZaxuJo2ZHZ
```

При смене VPS/host key обновите эту строку после независимой проверки нового ключа.
Workflow использует `StrictHostKeyChecking=yes`; host key не скачивается в ходе CI.
Секреты создаются в Settings → Secrets and variables → Actions → New repository secret.
Нужен вход в GitHub с правом настройки этого репозитория.

После настройки опубликуйте workflow в `main`. Первый push уже запустит проверки
и деплой. Убедитесь, что GitHub Actions разрешены в настройках репозитория.

## Подготовка, переключение и откат

На VPS отдельная transient systemd service `uhuru-deployment` выполняет обновление
под серверной блокировкой. Обрыв SSH не останавливает эту задачу. Git архивирует
точный SHA, npm устанавливает только production dependencies с `--ignore-scripts`
от имени `uhuru-build`; приложение в это время продолжает работать. Подготовленная
версия становится root-owned. Затем `deploy/db-setup.ts` новой версии применяет миграции
под системным пользователем `postgres` через локальный Unix socket, без отдельного
административного пароля. При ошибке миграций ссылка и работающий сервис остаются
прежними. После успешных миграций ссылка заменяется атомарно, сервис перезапускается.
Предыдущая версия с её `node_modules` сохраняется.

Проверка запуска ждёт до 15 секунд: сервис active, стабильный PID и открытый
TCP listener `127.0.0.1:8080` в течение пяти последовательных проверок. При ошибке
ссылка возвращается к старой версии, выполняются перезапуск и такая же проверка,
а задача завершается с ошибкой. Запись `pending` и systemd `ExecStopPost` позволяют
восстановить прежнюю версию при прерванном переключении.

Обычный перерыв ожидается в пределах 60 секунд. Это не гарантия восстановления
при неисправности самого VPS, systemd или БД. Проверка запуска не подтверждает
корректность HTTP/API и бизнес-логики: функциональную проверку проводит администратор.
Падение после завершения проверки запуска также не вызывает автоматический откат.

Для ручного возврата предыдущей версии подключитесь обычным SSH-доступом:

```sh
sudo /usr/local/sbin/uhuru-deploy rollback
```

Задача переживает обрыв SSH; команда ждёт её завершения. Успешный ручной откат
позволяет той же командой вернуться к версии, с которой откатывались.
Повторный запуск workflow/новый push снова попытается развернуть актуальный `main`.

Диагностика на VPS:

```sh
sudo journalctl -u uhuru-deployment --no-pager -n 100
sudo systemctl status uhuru-control-plane.service --no-pager
readlink -f /opt/uhuru
```

Старые версии сохраняются для ручного возврата. Автоматического удаления нет;
при заполнении диска удаляйте только неиспользуемые каталоги, сохраняя текущую
версию и SHA из `/var/lib/uhuru-deploy-state/previous` и `pending`, если он существует.

## Схема БД и системные настройки

Для перехода на node-config сначала выполните [подготовку конфигурации и unit](node-config-transition.ru.md).
Автодеплой не переносит секреты и не переустанавливает unit.

Для перехода с `database_socket` на отдельные поля подключения сначала выполните
[подготовку PostgreSQL, настроек и systemd unit](database-password-transition.ru.md).
Она сохраняет работу старой версии при автоматическом откате.

Новые файлы в `migrations` применяются автоматически перед переключением версии.
Уже существующие миграции нельзя менять, удалять или переименовывать: добавляйте
следующую миграцию. Проверка действует и с `--schema-reviewed`.

Каждая новая миграция должна быть совместима с работающей предыдущей версией:
она остаётся активной во время миграций и используется при автоматическом откате.
Откат возвращает код приложения, а не схему БД; `down` автоматически не выполняется.

Изменение tracked `*.sql` вне `migrations` по-прежнему останавливает автодеплой.
Скрипт не меняет `/etc/uhuru/local.json`, nginx, пароль роли приложения или
системные пакеты. Начальные миграции нельзя выполнять поверх существующих таблиц.
Перед первым деплоем на существующую БД выполните
[переход на миграции](database-migrations.ru.md).

После отдельно проведённого обновления БД и проверки совместимости **обеих**
версий приложения с новой схемой администратор может выполнить:

```sh
sudo /usr/local/sbin/uhuru-deploy deploy CHECKED_MAIN_SHA --schema-reviewed
```

Используйте SHA успешно проверенного workflow. Опция подтверждает отдельную
проверку схемы и совместимости для автоматического отката; она недоступна SSH-ключу
GitHub. Ручная команда `rollback` также блокирует переход через изменения SQL.
После отдельной проверки совместимости предыдущего кода с текущей БД администратор
может выполнить `sudo /usr/local/sbin/uhuru-deploy rollback --schema-reviewed`.

При изменении deployment scripts переустановите их отдельно через установщик:
сервер не исполняет новую версию root-script прямо из загруженного checkout.

## Проверки scripts

```sh
bash -n deploy/uhuru-deploy deploy/setup-autodeploy.sh deploy/setup-database.sh
python3 test/deploy_test.py
```

Тесты создают временные локальные Git-репозитории и подменяют системные команды.
Они проверяют подготовку, отказ npm, неудачный старт/отсутствие listener, оба отката,
миграции до переключения, отказ миграций без перезапуска, неизменность старых
миграций, SQL gate, устаревший commit, новый push во время подготовки,
блокировку и SSH whitelist.
Они не изменяют production и не заменяют проверку установки на реальном systemd.
