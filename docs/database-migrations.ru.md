# PostgreSQL: установка и переход на миграции

Схема и права роли приложения хранятся в `migrations`, история в `public.pgmigrations`.
Их применяет `deploy/db-setup.ts` (библиотека `node-pg-migrate`) от имени `postgres`
через `/var/run/postgresql` с peer-аутентификацией. Приложение работает под
ограниченной ролью `uhuru` по TCP с паролем.

## Новая установка

Подготовьте Node.js, PostgreSQL и системного пользователя `uhuru` по README.
Установите зависимости в проверенном root-owned `/opt/uhuru`, настройте подавление
журналов PostgreSQL и создайте `/etc/uhuru/local.json` с режимом root:uhuru `0640`.
Пароль приложения задаётся в `database.password`; отдельный пароль мигратора не нужен.

Из `/opt/uhuru` установите и запустите скрипт:

```sh
sudo install -o root -g root -m 0755 deploy/setup-database.sh /usr/local/sbin/uhuru-setup-database
sudo /usr/local/sbin/uhuru-setup-database
```

Скрипт создаёт недостающую БД, применяет миграции (первая создаёт роль `uhuru`) и
задаёт роли пароль из настроек, если пароля ещё нет. Пароль читает пользователь
`uhuru` и передаёт `postgres` через pipe, без вывода, argv и environment.
Существующие данные и пароль роли не меняются. Повторный запуск применяет только
новые миграции. Затем можно запускать приложение.

## Существующая БД без истории миграций

Начальную миграцию нельзя исполнять поверх существующих таблиц.
Перед включением нового деплоя:

1. Сверьте определения таблиц, ограничения, функцию `active_profiles`, настройки
   `service_settings` и права роли с `migrations/20261010000000000_schema.sql`.
   Данные пользователей и текущее значение цены сохраняются; они не являются
   причиной пересоздавать БД. Если схема отличается, сначала согласуйте отдельный
   переход. Убедитесь, что таблица `pgmigrations` отсутствует или пуста.
2. Только после подтверждения соответствия отметьте начальную миграцию
   как уже применённую:

    ```sh
    sudo runuser -u postgres -- psql -X -v ON_ERROR_STOP=1 -d uhuru <<'SQL'
    CREATE TABLE IF NOT EXISTS pgmigrations (id serial PRIMARY KEY, name varchar(255) NOT NULL, run_on timestamp NOT NULL);
    INSERT INTO pgmigrations (name, run_on) VALUES ('20261010000000000_schema', now());
    SQL
    ```

    Не повторяйте это для последующих миграций или для БД, соответствие которой не проверено.

3. Переустановите `uhuru-deploy` через существующий `setup-autodeploy.sh` из
   проверенной версии по [инструкции автодеплоя](autodeploy.ru.md), затем разверните
   проверенный SHA. Если SQL gate остановил удаление старых SQL-файлов, после
   проверки соответствия схемы выполните первый деплой с `--schema-reviewed`.
   Новые миграции будут применяться перед переключением релиза.

Обычный деплой не создаёт БД и не меняет пароль приложения.
При ошибке миграций работающий релиз не перезапускается.
Автоматический откат меняет код, сохраняя схему БД: новые миграции должны быть
совместимы с предыдущей версией. Миграции, уже попавшие в релиз, не редактируют,
не удаляют и не переименовывают. Новый файл создаётся командой
`npm run db:migration -- <name>`.
